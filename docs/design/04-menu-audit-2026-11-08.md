## วิธีตรวจและขอบเขตหลักฐาน

- เรนเดอร์ **29 หน้าจอ/สถานะ × 2 profiles = 58 cases** ด้วย widgets จริงและฟอนต์ Inter ที่ bundled ในแอป ใช้ข้อมูลสังเคราะห์ ไม่อ่านข้อมูลจริงของผู้ใช้
- Profiles: 390×844 logical pixels / text 100% และ 320×844 / text 200%, พร้อม safe-area insets จำลอง และภาพท้ายหน้าสำหรับหน้าที่เลื่อนได้
- ดูภาพจริง อ่าน source ของ routes/สถานะ และวัดขนาด tap targets จาก render tree
- เพิ่ม audit contracts 5 ข้อเพื่อพยายามหักล้าง UX invariants: **ทั้ง 5 ข้อล้มเหลวตามปัญหาที่พบจริง** อยู่ใน `tool/design_audit/` จึงไม่ถูกเพิ่มเข้า default product test suite
- Analyzer ของ audit harness ทั้งสองไฟล์ผ่านโดยไม่มี issues; ไม่ใช่การรับรอง analyzer ทั้งแอป
- Capture harness จบครบ ไม่ได้หมายความว่าแอปผ่าน: harness ตั้งใจบันทึก layout errors ลง JSON แล้วถ่ายภาพต่อ
- ที่ขนาดปกติไม่พบ RenderFlex overflow ใน 29 cases แต่ยังพบ warning เรื่อง ListTile ink ใน Logbook overview; ที่ profile ใหญ่พบ overflow ใน **16/29 cases รวม 51 error events** จำนวน events อาจรวมการเรนเดอร์หลายครั้ง ไม่ใช่จำนวนบั๊กที่ไม่ซ้ำ
- ไม่ได้ทดสอบอุปกรณ์จริง, แสงแดด, VoiceOver/TalkBack จริง, กล้อง/permission จริง, auth จริง, sync ขณะ offline, keyboard ทุกแบบ, ข้อมูลปริมาณมาก หรือ usability sessions กับ tradie/นักบัญชี การวิเคราะห์จิตวิทยาด้านล่างเป็น **expert hypothesis** จากรูปแบบ UI ไม่ใช่ผลวิจัยผู้ใช้

## สิ่งที่ควรเก็บไว้

1. ฟอร์ม Logbook แบบใหม่ใช้คำถามตามงานจริง เช่น “What was the trip for?” และแยกกลุ่มข้อมูลชัด เหมาะเป็นต้นแบบให้ฟอร์ม CPK
2. หน้า Review evidence มีรายการงานจริง ใช้ข้อความร่วมกับไอคอน แยก “Share draft records” จาก “Share records” และตรวจไฟล์ก่อนแชร์ เป็นแกน workflow ที่ดี
3. หน้า Feedback อธิบายว่าไม่แนบ records และให้ preview ก่อนส่ง ช่วยสร้างความคาดเดาได้ของการกระทำ
4. รายการรถมี search + รายการยอดนิยม + manual fallback เป็นโครงสร้างที่เข้าใจง่าย
5. ชุดสีหลักเริ่มสอดคล้องกันแล้ว รายการและเอกสารอ่านสะอาด ไม่จำเป็นต้องเริ่ม visual identity ใหม่

### F01 · P1 — หน้า Tax บอกว่าเรียบร้อยทั้งที่ยังมีงานค้าง

**พบจริง:** ข้อมูลชุดเดียวกันแสดง `92%`, สีเขียว, `Details up to date` และ `3 items need attention` ในการ์ดเดียวกัน หน้า Compliance แสดง `92% Tax-Ready` และ “evidence chain is complete” แต่มีทริปขาด purpose

**เหตุ:** ชื่อสถานะอิง threshold ของคะแนน (`score >= 90`) แทนการเสร็จของเงื่อนไขจริง คะแนนมีส่วนของการตั้งค่ารถ/วิธีภาษี จึงไม่ใช่หลักฐานว่า record แต่ละรายการพร้อม

**ผลต่อผู้ใช้ที่คาด:** คนที่เหลือบดูสี/หัวเรื่องอาจหยุดแก้ก่อนครบ นักบัญชีต้องย้อนถามข้อมูลอีก ความมั่นใจที่ UI สร้างสูงกว่าหลักฐาน

**ข้อเสนอ:** ใช้จำนวนงานค้างและประเภทงานเป็นตัวนำ คะแนน setup แยกออกจาก record checks; แสดง `3 records to review` จนกว่าจะตรวจครบ แม้ไม่ค้างก็ควรสื่อ “Ready for accountant review” ตามขอบเขตที่ตรวจจริง

## แนวทางออกแบบที่เสนอสำหรับทั้งระบบ

**แกนของประสบการณ์:** `Capture → Check missing details → Review records → Share with accountant` แต่ละหน้าตอบคำถามเดียวให้ชัด:

| จุดใช้งาน | คำถามหลักของผู้ใช้ | ข้อมูลนำ | การกระทำหลัก |
|---|---|---|---|
| Home | วันนี้ต้องทำอะไรอีก? | งานค้างและสิ่งที่บันทึกล่าสุด | ทำรายการถัดไป |
| Trips | ทริปไหนยังขาดรายละเอียด? | route, date, purpose/classification | เติม/ยืนยันทริป |
| Expenses | ใบไหนต้องแนบหรือยืนยัน? | merchant, amount, receipt/review state | เพิ่มหลักฐาน/ตรวจรายละเอียด |
| Tax | จำนวนประมาณเท่าไร และตั้งอยู่บนข้อมูลใด? | estimate + FY/vehicle + assumptions | ตรวจรายการประกอบ |
| Review/share | ส่งอะไรไป มีอะไรยังไม่ครบ? | scope, checks, actual files, draft state | preview แล้วแชร์ |
| Settings | ข้อมูลอยู่ไหน สำรองล่าสุดเมื่อไร? | local/backup state ที่พิสูจน์ได้ | สำรอง/จัดการข้อมูล |

สีขาวอุ่นเป็นพื้นดำเนินงาน ดำเป็นเนื้อหาและโครงสร้าง ส้มเข้มเป็น action; เขียวใช้กับเงื่อนไขที่ตรวจสำเร็จแล้ว, amber กับสิ่งที่ผู้ใช้ต้องทำ, แดงกับความผิดพลาดที่ต้องแก้ ไม่ต้องบังคับเปอร์เซ็นต์สีเท่ากันทุกหน้าจอ

**สมมติฐานด้านจิตวิทยาที่ควรนำไปทดสอบ:** กลุ่ม tradie น่าจะได้ประโยชน์จากการเห็น “เหลือ2รายการ” มากกว่าคะแนน92% ที่ไม่รู้สูตร; นักบัญชีน่าจะให้ค่ากับ scope, exceptions และความครบของหลักฐานมากกว่า badge premium ความต่อเนื่องของสถานะและคำเรียกจะช่วยสร้างความมั่นใจที่อิงสิ่งที่ทำสำเร็จจริง สมมติฐานเหล่านี้ต้องยืนยันด้วย task-based research ไม่ใช้ความชอบสีเป็นตัวแทนผลลัพธ์

## ลำดับลงมือที่แนะนำ

1. **ความจริงและความต่อเนื่อง:** F01–F05, F10, F16; ใช้สถานะ review กลาง, แก้ route “View”, ทำ draft/share และคำรับรองให้ตรงสิ่งที่ตรวจได้

3. **ขอบเขตและโครงงาน:** F06, F11–F14; คง context รถ/FY และแยก expense total/deduction, แก้ empty state
4. **ความสม่ำเสมอทางภาพ:** F17–F18; ทำ forms/type/component variants ให้เป็นระบบเดียว แล้วทดสอบกับผู้ใช้
